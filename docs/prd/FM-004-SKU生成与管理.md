## 一、业务背景

运营已经能创建商品 SPU，但仓储和订单需要识别具体的可售单元。
例如“基础款 T 恤”是 SPU，“黑色 / M 码”是 SKU。
运营希望基于已有 SPU 规格一次生成 SKU，再逐个维护售价和图片。

已有规格示例：

```json
[
  {"name": "颜色", "values": ["黑色", "白色"]},
  {"name": "尺码", "values": ["S", "M", "L"]}
]
```

应生成 6 个不同组合，每个 SKU 在每个规格维度恰好选择一个值。
不能漏组合，也不能生成“黑色 / 白色”这样的同维度组合。

## 二、本次范围

1. 根据数据库内 SPU 的规格生成 SKU；客户端不提交最终组合清单。
2. 查询某个 SPU 下的 SKU，返回顺序稳定，包含规格组合、价格、图片和版本号。
3. 根据 SKU ID 查询详情。
4. 修改 SKU 的售价和图片，使用版本号避免并发覆盖；不能借编辑接口修改归属、编码或规格组合。
5. 补上生成 SKU 后的 SPU 规格修改保护，避免既有 SKU 与 SPU 定义不一致。
6. 通过自动化测试、真实 MySQL 验收及 PR 完成交付。

本卡不做：库存与库存扣减、订单、秒杀、Redis 缓存、MQ、商品上下架状态机、SKU 删除与复杂重建。
生成和编辑暂限定草稿 SPU，查询允许读取其他状态的未删除 SPU 下的有效 SKU。
SKU 初始价格、无规格商品、重复生成等规则按下一节评审结果确定。

## 三、需求澄清：先提交判断和理由，再写代码

下面是待决策问题，不是已确定的实现要求。按“选择 + 理由 + 失败时如何提示”回答。

1. **没有规格怎么办？** `specs=[]` 是 FM-003 的合法数据。生成一个默认 SKU，还是拒绝生成？默认组合怎么表示？
2. **重复生成怎么办？** 已经生成过，再点击生成，是返回现有结果、拒绝，还是重建？如果运营已经改过价格和图片，如何避免丢失？
3. **生成数量上限是多少？** 当前规格允许最多 `20×20×20=8000` 种组合。提出本期业务上限；超限时整体拒绝还是截取？必须在分配全部组合对象之前判断。
4. **价格怎么约定？** 生成时统一指定价格，还是先待定？是否允许 0 元？币种、最大值和小数位是什么？超过精度拒绝还是舍入？Java 和 MySQL 分别用什么类型？
5. **SKU 身份如何确定？** 编码由谁生成、在哪个范围唯一？同一 SPU 下如何判断两个组合相同？规格顺序变化或值里包含分隔符时，会不会误判？
6. **生成后还能改 SPU 规格吗？** 新增、删除、重命名、仅调整顺序分别怎么处理？本期不做复杂重建，但仍要允许正常修改商品名称、图片等非规格字段。
7. **图片如何初始化和修改？** 生成时是否复制 SPU 主图？SKU 图片留空意味着清空、回退还是非法？SPU 主图后来修改时，已有 SKU 图片是否跟着变化？
8. **并发和失败如何处理？** 两个请求同时生成，或生成期间另一个请求修改 SPU 规格，如何保证结果一致？第二批插入失败时，第一批是否保留？哪些写入口必须共同遵守锁定/版本协议？

### 澄清结论（2026-09-28）

1. 无规格生成一个默认 SKU，组合为 `[]`；存在维度但候选值为空属于非法规格。
2. SPU 已有有效 SKU 时拒绝再次生成，不覆盖、不补齐、不重建，保留原价格和图片。
3. 单个 SPU 最多 1000 个 SKU，先计算数量再构建组合；超限整体拒绝，单批写入最多 500 条。
4. 统一初始价格必填，范围 0.00～99999999.99，最多两位小数；Java 用 BigDecimal，MySQL 用 DECIMAL(10,2)，超精度拒绝而非舍入。
5. 编码由后端生成，全局唯一且永不复用；有效组合以 `(spu_id, spec_hash, deleted)` 唯一约束兜底。哈希的规范化算法仍需单独评审。
6. 有有效 SKU 后冻结 SPU 规格，包括新增、删除、重命名和重排；规范化后完全相同的规格允许提交，非规格字段按原规则修改。
7. 生成请求只接收统一 price 和可选 imageUrl。图片未传或空白时复制当时的 SPU 主图 URL，后续不自动跟随；编辑图片必填。
8. 生成与 SPU 规格修改需要遵守同一 SPU 行锁协议，全部批次属于同一事务，中途失败全部回滚。具体锁顺序与流程仍需提交方案。

### 当前模型与迁移说明

- `SkuGenerateDTO` 不接收客户端组合列表；已移除不再使用的 `SkuGenerateItemDTO`。
- `SkuSpecValueDTO` 表示一个维度的一个选中值，Entity 与 VO 均使用其列表；它不是候选规格列表 SpecDTO。
- 本期不接收/返回库存、市场价或未定义的 SKU 状态；specHash 只在内部使用。
- 保留 V6 不再修改；V7 补充 SKU 编码唯一索引。若存在重复编码，需核查数据再迁移，不自动清理。
- 已补参数校验和实体 JSON 映射测试；尚未执行真实数据库迁移、并发及回滚验证。

### 组合生成器契约（2026-10-01）

- `SpecCombinationGenerator.generate(List<SpecDTO>)` 返回 `List<List<SkuSpecValueDTO>>`，与 SPU 规格和 SKU JSON 字段直接衔接。
- 保留输入维度及候选值顺序，最后一个维度变化最快；空输入列表返回 `[[]]`，表示一个默认 SKU。null 输入拒绝，不等同于无规格。
- trim 使用与 SPU 一致的规则；校验空白、长度、维度数量、候选值数量、重复名及同维度重复值。不同维度可以有相同值。
- 先做数量预检，再展开组合；覆盖 1000 通过、1001 拒绝。生成器不计算哈希、不生成编码、不访问数据库。
- 两层输出列表不可增删；DTO 本身仍可变，但每个组合项独立，修改一项不影响其他组合或输入。不要把列表不可变误认为元素也不可变。
- 异常用例必须实际调用生成器并断言业务错误码，不能只准备测试数据。

## 四、技术方案：由开发填写

### 4.1 表结构与对象

- 提交 `product_sku` DDL：主键、SPU 归属、SKU 编码、规格组合、金额、图片、审计字段、deleted、version。
- 解释每个唯一约束保证什么，以及逻辑删除后的唯一性语义；不能只靠应用查询防重。
- 解释组合标识的规范化方式，不能简单用未转义的分隔符拼接。
- 列出 Entity、DTO、VO、转换器的职责；DTO 不得直接接收内部审计字段。
- 使用下一个未占用的 Flyway 版本，不修改已经执行过的迁移。

### 4.2 接口草案（评审后定稿）

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/product/admin/spus/{spuId}/skus/generate` | 基于已存规格生成 SKU |
| GET | `/api/product/admin/spus/{spuId}/skus` | 查询 SPU 下的 SKU |
| GET | `/api/product/admin/skus/{id}` | SKU 详情 |
| PUT | `/api/product/admin/skus/{id}` | 修改价格、图片，携带 version |

补齐请求/响应示例、参数约束、列表是否分页、排序规则和业务错误码。
不要把“SPU 不存在”和“SPU 存在但还没有 SKU”混成同一种响应。

### 4.3 关键流程

写出生成接口和 SKU 修改接口的伪代码，至少说明：

- SPU 存在、未删除、草稿状态的检查位置。
- 组合数预检、笛卡尔积生成、组合身份的确定过程。
- 重复请求、并发生成和 SPU 规格修改之间的协调方式。
- 单批不超过 500 条；多批如何处于同一个事务，失败如何退出。
- 影响行数异常、唯一冲突、乐观锁冲突如何处理。
- 日志包含 spuId、生成数量等可用于排障的信息，不逐条打印整个 SKU 列表。
