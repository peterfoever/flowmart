## 一、需求背景

> 以下是产品经理给你的原始描述。真实工作中的需求就是长这样的 ——
> 有背景、有诉求，但**细节全是模糊的**。你的第一项工作不是写代码，是把它问清楚。

我们要上商品中心了。第一步得先把商品类目做出来，因为后面 SPU 建档、前台导航、
库存报表都要挂在类目上。

运营那边的诉求是：能自己维护一棵商品类目树，比如
「食品饮料 → 休闲零食 → 坚果炒货」这样一层层分下去。要能增删改查，能调顺序，
能临时把某个类目关掉不让它显示。前台要一次性拿到整棵树来渲染导航。

类目量级大概几百个，不会太多。这个先做出来，下周 SPU 就要用了。

### 4.3 分层结构（必须遵守，这是本项目的代码规范）
```
flowmart-product/
└── src/main/java/com/flowmart/product/
    ├── controller/     只做参数接收和响应包装，不写任何业务逻辑
    ├── service/        业务编排 + 事务边界
    │   └── impl/
    ├── mapper/         数据访问，只关心 SQL
    ├── entity/         数据库实体，与表一一对应
    ├── dto/            入参对象（Request/Command）
    ├── vo/             出参对象（给前端看的）
    ├── convert/        MapStruct 对象转换
    └── enums/          业务枚举 + 错误码
```

> **为什么要 DTO / Entity / VO 三套对象？**
> 直接拿 Entity 收参数和返回，会导致：① 前端能篡改 `deleted`、`version` 这类不该给它的字段；
> ② 密码、成本价这种敏感字段会泄露出去；③ 表结构一改，接口契约就跟着崩。
> 这三条在实际项目里都出过事故，不要图省事。
